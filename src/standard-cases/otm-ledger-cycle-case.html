OnTheMarket · Solved issue 04

장부·상품 서비스의 순환 의존 해소

가입 후 주문을 시작하지 않거나 가격 확인 단계에 도달하지 못한 점주도 서비스의 가격을 경험할 수 있도록, 튜토리얼에서 식자재를 고르고 견적을 요청한 뒤 카카오톡으로 결과를 받는 흐름을 만들었습니다. 이 알림에 필요한 음식점 정보와 유통업체 가격을 조회하면서 서비스 간 의존이 순환하지 않도록 구조를 정리했습니다.

Problem & constraints

주문을 시작하기 전에도 “여기서 사면 얼마인지” 알 수 있어야 했습니다.

온더마켓은 음식점 점주가 식자재를 고르고 유통업체를 비교해 주문하는 서비스입니다. 기존에는 주문할 식자재를 담은 뒤 유통업체를 선택하는 단계까지 가야 업체별 가격을 확인할 수 있었습니다. 가입과 온보딩을 마쳐도 주문을 시작하지 않거나 그 단계까지 도달하지 못하면, 점주는 실제 구매 가격을 확인하지 못한 채 이탈할 수 있었습니다.

그래서 주문 흐름을 끝까지 진행하지 않아도 가격을 경험할 수 있는 튜토리얼을 만들었습니다. 점주가 자주 사는 식자재를 고르면 예상 최저가를 보여주고, “견적받고 온더마켓 시작하기”로 견적을 요청할 수 있게 했습니다. 이후 공급 가능한 유통업체의 가격을 비교해 카카오톡으로 알려주고, 알림에서 업체 비교·주문 화면으로 다시 이어지도록 했습니다.

  1. 튜토리얼에서 구매할 식자재와 수량을 선택하고 예상 가격을 확인합니다.
  2. 견적을 신청하면 선택한 품목을 저장하고, 결과가 준비되면 카카오톡으로 안내합니다.
  3. 점주는 알림에 담긴 최저가 업체·금액을 보고 업체 비교 또는 주문 화면으로 이동합니다.

이 사용자 흐름을 서버에서 처리하는 방식

Ledger 장부
식자재와 수량을 저장하는 목록입니다. 견적 신청 시 선택한 품목으로 새 장부를 만들고 quote 상태로 저장합니다. 여기서 quote는 견적 결과 알림을 기다리는 요청을 뜻하며, 발송 성공 후에는 closed로 바꿉니다.
Restaurant 음식점
알림을 받을 음식점의 이름과 전화번호를 제공합니다.
Distributor 유통업체
선택한 식자재와 수량에 대한 업체별 총액을 계산하고, 최저가 업체를 찾습니다.
Catalog 상품
식자재의 기준 정보입니다. 장부와 유통업체 가격표가 같은 상품을 참조하며, 판매를 중단한 상품은 장부에서도 정리해야 합니다.

정기적으로 작동되는 배치서비스가 quote 상태인 ledger가 있고 해당 음식점에 식자재를 입찰한 유통업체(BidTicket)가 3건 이상이면 음식점에 알림을 보냅니다. 이 처리를 맡은 LedgerService에는 각 유통업체별 식자재 가격을 조회하는 DistributorService와 수신자 정보를 조회하는 RestaurantService가 추가로 inject되어야해졌습니다.

Observed before

기존에 RestaurantService는 장부 목록을 조회했을 때 장부가 없으면 기본 장부를 만들고, 그 id를 restaurant.ledgers에 넣기 위해(initLedger) LedgerService를 주입받았고, CatalogService는 상품 비활성화 시 모든 장부의 lineItems에서 그 상품을 지우려고(removeAllLineItemsByCatalogId) 역시 LedgerService를 주입받았습니다. DistributorService는 가격표 갱신과 입찰 처리를 위해 원래부터 CatalogService·RestaurantService·BidTicketService에 의존했습니다. 이 상태에서 장부 서비스가 유통업체·음식점 서비스를 다시 주입받으면 아래와 같은 순환 경로가 생깁니다.

DistributorService→ CatalogService→ LedgerService→ DistributorService↺ 순환
RestaurantService→ LedgerService→ RestaurantService↺ 순환

Solution

견적 알림에 필요한 장부 → 유통업체·음식점 의존은 두고, 상품·음식점 서비스에서 장부 서비스를 직접 주입받던 부분을 제거했습니다. 백엔드 라우팅 단계인 catalog.signal.ts에서 두 서비스를 순서대로 호출하도록 바꿨습니다. 먼저 CatalogService.inactivateCatalog로 상품을 비활성화하고, 이어서 LedgerService로 장부에서 해당 품목을 지웁니다. initLedger는 RestaurantService에서 LedgerService로 옮겨 장부를 만든 뒤 restaurantService로 식당의 ledgers를 갱신하게 했고, restaurant.signal.ts가 ledgerService.initLedger를 부르게 했습니다.

LedgerService→ DistributorService· RestaurantServiceCatalog·Restaurant의 LedgerService 주입 제거

Code change

백엔드 라우팅 단계에서 상품 서비스와 장부 서비스를 순서대로 호출했습니다.

Beforecatalog.service.ts가 ledgerService를 직접 호출
@Service("CatalogService")
export class CatalogService extends DbService(db.catalogDb) {
  @Srv() ledgerService: srv.LedgerService;

  async inactivateCatalog(catalogId: string) {
    const catalog = await this.getCatalog(catalogId);
    await catalog.set({ status: "inactive" }).save();
    await this.ledgerService
      .removeAllLineItemsByCatalogId(catalogId);
  }
}
Aftercatalog.signal.ts에서 두 서비스를 차례로 호출
// catalog.signal.ts
@Mutation.Admin(() => Boolean)
async inactivateCatalog(
  @Arg.Body("catalogId", () => String) catalogId: string
) {
  await this.catalogService.inactivateCatalog(catalogId);
  await this.ledgerService
    .removeAllLineItemsByCatalogId(catalogId);
  return true;
}

// ledger.service.ts
@Srv() distributorService: srv.DistributorService;
@Srv() restaurantService: srv.RestaurantService;

Outcome & trade-off

알림에 필요한 조회를 연결하면서 역방향 의존을 제거했습니다.

Outcome Ledger → Distributor · Restaurant 단방향

LedgerService가 음식점 정보와 유통업체 가격을 조회할 수 있게 하고, CatalogService·RestaurantService가 다시 장부 서비스를 주입받는 관계를 제거했습니다.

Trade-off 상품 비활성 후 장부 정리 실패 가능

첫 호출은 성공하고 두 번째가 실패하면 상품은 비활성인데 장부에는 품목이 남는 중간 상태가 생깁니다. 트랜잭션이나 보상 로직은 두지 않았습니다.

두 호출을 순서대로 실행하는 것만으로 함께 성공하거나 함께 취소되는 것은 아닙니다. 상품 상태 변경 후 장부 정리가 실패하면 중간 상태가 남을 수 있으며, 이 부분은 트랜잭션이나 실패한 정리 작업의 재시도로 보완할 수 있습니다.
