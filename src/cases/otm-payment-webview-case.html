OnTheMarket · Solved issue 01

PG 페이지를 다녀온 뒤 WebView 레이아웃 복원

다른 앱으로 내보내지 않고 웹뷰 안에서 결제사 페이지를 오가게 하면서 생긴 inset 문제를 한 단계씩 좁혀, 복귀 시 safe-area·viewport가 다시 계산되도록 native에서 맞춰줬습니다.

Problem & constraints

결제는 직접 제어할 수 없는 외부 페이지를 웹뷰 안에서 다녀와야 했습니다.

앱 안에서 결제를 하려면 직접 제어하기 곤란한 TossPayments 같은 외부 결제사(PG) 페이지를 거쳐야 했습니다. 팝업이나 별도 앱·브라우저로 나갔다가 다시 돌아오는 방식은, 휴대폰에 시간을 많이 쓰고 싶어 하지 않고 연령대가 꽤 있는 식당 점주들에게 어려울 수 있다고 판단했습니다. 그래서 다른 앱으로 나가는 리다이렉트를 최소화하고, 웹뷰 안에서 실제 URL을 바꿔 결제사 페이지로 갔다가 돌아오는 플로우를 택했습니다.

기존 웹앱 구조는 웹페이지와 앱을 같은 코드로 운영하기 위해 휴대폰 화면 전체를 웹뷰로 덮고, 노치·홈 인디케이터 같은 safe-area(inset)는 Capacitor로 감지해 CSS 값으로 웹 레이아웃에 넘겨주는 방식이었습니다. 내부 화면에서는 웹이 safe-area를 소유했습니다.

외부 PG 페이지에서는 이 방법을 쓸 수 없었습니다. PG사 웹사이트는 CSS로 제어할 수 없는 외부 문서라 native 단에서 WebView의 inset을 직접 다뤄야 했고, 그 과정에서 아래 문제들이 순서대로 나타났습니다.

내부 주문 화면웹이 safe-area 소유→ 외부 PG 페이지native가 inset 소유→ 카드·은행 앱intent / scheme으로 OS에 위임→ 내부 결과 화면다시 웹이 소유해야 함

Observed before

inset을 안 넣으면 결제 버튼이 가려지고, 넣으면 돌아온 화면이 깨졌습니다.

처음에는 PG 페이지를 그냥 두었습니다. 웹뷰가 화면 전체를 덮는 구조라 외부 문서는 inset이나 margin 없이 떴고, Android에서 메뉴·홈·뒤로가기 3버튼 내비게이션 바를 켜 둔 기기에서는 시스템 바가 결제사의 “결제하기” 버튼을 그대로 덮었습니다. 불편한 수준이 아니라 결제 자체가 불가능한 경우였습니다.

그래서 외부 URL일 때 native에서 URL을 감지해 inset을 넣어줬더니, 결제를 마치고 앱 페이지로 돌아오면 바텀 탭이 위로 떠 버렸습니다. 복귀 시점에 inset과 safeArea를 초기화하는 코드를 넣었더니, 이번에는 바텀 탭이 화면 아래에 박혀 버렸습니다.

여백 유실 native는 돌아왔지만 웹은 다시 재지 않음

inset을 0으로 되돌려도 웹이 부팅 때 저장해 둔 safe-area·innerHeight 값은 외부 페이지 기준으로 남아, 하단 안전 영역 없이 배치됐습니다.

초기화만으로 왜 안 되는지 알아야 했는데, safe-area를 계산하는 코드가 앱 코드 어디에도 보이지 않았습니다. Capacitor에서 inset을 웹으로 전달하는 부분이 사용중이던 akanjs 프레임워크의 node_modules 안에 들어 있었기 때문입니다. AI 도구로도 원인을 찾지 못해서 node_modules를 직접 열어 조사했습니다.

읽어 보니 @akanjs/client의 device.init()이 앱 부팅 시 capacitor-plugin-safe-area의 getSafeAreaInsets()를 한 번 호출해 상·하단 safe-area를 저장하고, @akanjs/next는 window.innerHeight도 부팅 시 한 번 useRef에 잡아 페이지 높이와 하단 safe-area 밴드 위치 계산에 계속 사용했습니다. @akanjs/ui는 #topSafeArea·#bottomSafeArea라는 fixed div를 웹이 직접 그렸습니다. safe-area와 viewport 높이는 웹 레이어가 부팅 시 한 번 재고, 그 뒤로는 다시 재지 않는 구조였습니다. 결제 왕복 중 native가 inset을 켰다 끄면 WebView의 geometry가 바뀌는데 웹은 그 사실을 모르니, 복귀 시 native 값을 원복하는 것만으로는 부족했고 웹이 다시 재도록 신호까지 보내야 했습니다.

Solution

복귀 시 native inset을 원복하는 데서 그치지 않고, 웹이 다시 재도록 신호를 보냈습니다.

웹 레이어의 설계를 바꾸는 대신 native가 맞춰주기로 했습니다. 먼저 로드되는 main-frame URL이 내부(capacitor·localhost·개발 서버 사설 IP)인지 외부인지 판별합니다. 외부면 native가 inset을 켜서 PG 페이지가 잘리지 않게 하고, 카드·은행 앱 호출은 intent나 custom scheme으로 OS에 넘깁니다. 내부로 돌아오면 inset을 끄고, 그 자리에서 웹 레이어가 safe-area와 viewport를 다시 재도록 OS마다 다른 방식으로 신호를 보냈습니다.

진행 순서

2025-10-01 Android에서 intent·custom scheme으로 외부 결제 앱을 호출하는 것부터 시작했고, 10-30 iOS도 custom scheme을 UIApplication.open으로 넘겼습니다. 10-31 iOS에 URL별 inset 전환과 didFinish 재판별을 넣고, 11-02 결제 결과 페이지와 레이아웃을 정리한 뒤, 11-10 Android에 WindowInsets margin과 CSS 변수 재주입을 붙였습니다. iOS의 0.1pt reflow와 resize 재계산은 그 뒤에 추가했습니다.

Outcome & trade-off

웹이 레이아웃을 소유하는 프레임워크의 설계를 깨지 않고 결제 왕복을 붙였습니다.

akanjs가 safe-area를 웹으로 넘겨 웹이 레이아웃을 소유하게 한 것은, 웹과 크로스플랫폼 앱을 한 코드베이스로 만들고 제스처·페이지 트랜지션을 웹에서 구현하기 쉽게 하려는 의도였고, 맞는 설계였다고 생각합니다. 다만 그 설계를 유지하려면 외부 PG 페이지처럼 웹이 손댈 수 없는 구간을 native가 대신 맞춰줘야 했고, 이 작업이 그 번잡한 부분이었습니다. 덕분에 “유지보수성이 높고 웹 코드로 모든 것을 제어할 수 있는 시스템”이라는 프레임워크의 의도를 깨지 않고 이어갈 수 있었습니다.

Kept 웹이 safe-area·레이아웃 소유

akanjs의 부팅 시 측정 구조와 웹 제스처·트랜지션 코드를 그대로 두었습니다.

Added native가 URL 경계에서 inset 전환

Android는 margin + CSS 변수 재주입, iOS는 contentInset 전환 + reflow로 웹이 다시 재게 했습니다.

Fixed PG 결제 버튼 잘림 · 복귀 후 레이아웃 붕괴

다른 앱으로 내보내지 않는 웹뷰 내 결제 플로우를 두 OS에서 유지할 수 있게 됐습니다.

Trade-off

iOS 복귀 reflow가 0.1pt 프레임 변경·50ms 지연 같은 휴리스틱에 기대고 있어 WebKit 동작이 바뀌면 깨질 수 있습니다.
