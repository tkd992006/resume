OnTheMarket · Solved issue 05

타입 서버를 느리게 만든 nullable 인자 타입 폭발 추적

웹 빌드가 10분을 넘기기 시작했을 때, 타입이 퍼져 나가는 곳은 signal뿐이라고 보고 프레임워크의 인자 튜플 타입에서 2ⁿ으로 불어나는 지점을 찾아냈습니다.

Problem & constraints

코드는 조금씩 늘었을 뿐인데 타입 검사 시간이 감당이 안 되기 시작했습니다.

온더마켓은 AkanJS 프레임워크 위에서 만든 서비스입니다. AkanJS에서는 GraphQL resolver를 *.signal.ts에 선언하면, 그 메서드 시그니처 하나에서 클라이언트 fetch 함수, store의 queryArgsOf…, 페이지 init 타입까지 TypeScript 타입으로 자동 파생됩니다. 서버 코드를 한 번만 쓰면 클라이언트 타입이 따라오는 구조라, 목록 조회에는 statuses·skip·limit·sort처럼 생략 가능한 필터 인자를 { nullable: true }로 자유롭게 붙여 왔습니다.

2025년 8월 중순, 유통사·상품·장부·식당 목록 화면을 한꺼번에 붙이면서 전체 API 인자 중 nullable 인자가 132개까지 늘었습니다. 그 무렵부터 에디터 타입 서버가 응답을 멈추기 일쑤였고, 웹 빌드는 10분을 넘겼습니다. 1인 개발이라 빌드 한 번이 곧 배포 주기여서, 출시 전 검수 일정 안에 원인을 찾아야 했습니다.

Observed before

타입이 퍼지는 곳은 signal뿐이니, 프레임워크의 인자 타입부터 열어 봤습니다.

서비스나 문서 모델은 타입이 그 파일 안에서 끝나지만, signal 메서드의 인자 타입은 프레임워크가 튜플로 받아 앱의 모든 클라이언트 타입으로 다시 찍어 냅니다. 그래서 느려진 원인이 어디든 증폭되는 지점은 signal이라고 보고, @akanjs/signal의 gql.ts에서 인자 튜플을 가공하는 FilterOutInternalArgs를 읽었습니다. 이 타입은 튜플을 앞에서부터 재귀하면서 Head extends undefined | null로 nullable 인자를 판정하고, nullable이면 [...Acc, Head?]로 optional 요소를 하나씩 쌓는 방식이었습니다.

문제는 infer Head로 뽑은 타입 파라미터에 조건부 타입을 걸면 TypeScript가 유니온을 분배한다는 점이었습니다. string | null은 string 가지와 null 가지로 갈라지고, 누적 중이던 튜플도 둘로 복제됩니다. nullable 인자를 하나 지날 때마다 튜플 유니온이 두 배가 되니, 인자 7개짜리 목록 조회 하나가 128개의 튜플 조합을 만들고, 그 조합이 fetch 함수·store·init 타입마다 다시 계산됐습니다.

nullable 인자 n개→ 분배 조건부 타입→ 튜플 유니온 2ⁿ개→ 파생 타입마다 재계산

Solution

당장은 nullable을 걷어내 출시를 지키고, 근본 수정은 프레임워크에 반영되게 했습니다.

먼저 온더마켓 쪽에서 목록 조회의 statuses·skip·limit과 검색 필터 인자에서 nullable을 빼고 클라이언트가 항상 값을 넘기도록 바꿨습니다. 마지막 인자인 sort만 nullable로 남겼는데, 튜플 끝에 하나 있는 nullable은 분기가 한 번뿐이라 부담이 없었기 때문입니다. 8월 19일부터 25일까지 두 커밋에 걸쳐 132개였던 nullable 인자를 80개, 다시 52개로 줄였고, 타입 서버와 빌드가 다시 돌아왔습니다.

동시에 원인 위치와 재현 조건을 AkanJS 쪽에 공유했고, 8월 28일 프레임워크 PR에서 FilterOutInternalArgs가 세 단계로 다시 쓰였습니다. 내부 인자 제거(FilterInternalArgs)와 타입 변환(ConvertArgs)을 분리하고, nullable 판정은 분배가 일어나지 않는 null extends Head로 바꾼 뒤, 첫 nullable 인자를 만나는 순간 나머지를 Partial<T> 한 번으로 처리합니다. 분기가 사라져 인자 수에 선형으로 끝납니다. 온더마켓은 9월 초 이 수정이 담긴 0.9.44로 올렸습니다.

Code change

분배되는 조건부 타입 하나를 비분배 판정과 Partial 한 번으로 바꿨습니다.

Before@akanjs/signal gql.ts · nullable마다 튜플이 두 갈래로
export type FilterOutInternalArgs<
  T extends any[], Acc extends any[] = []
> = T extends readonly [infer Head, ...infer Rest]
  ? IsInternalArg<Head> extends true
    ? FilterOutInternalArgs<Rest, Acc>
    // Head가 string | null이면 여기서 분배 →
    // Acc가 [.., string]과 [.., null?] 둘로 복제
    : Head extends undefined | null
      ? FilterOutInternalArgs<Rest, [...Acc, ConvertArg<Head>?]>
      : FilterOutInternalArgs<Rest, [...Acc, ConvertArg<Head>]>
  : Acc;
After비분배 판정 + 첫 nullable부터 Partial 한 번
type FilterInternalArgs<T extends any[]> =
  T extends [...infer Rest, infer Last]
    ? IsInternalArg<Last> extends true
      ? FilterInternalArgs<Rest> : T
    : [];

type PartialNullableArgs<T extends any[]> =
  T extends [infer Head, ...infer Rest]
    ? null extends Head        // 분배 없음
      ? Partial<T>             // 나머지를 한 번에
      : [Head, ...PartialNullableArgs<Rest>]
    : [];

export type FilterOutInternalArgs<Args extends any[]> =
  PartialNullableArgs<ConvertArgs<FilterInternalArgs<Args>>>;

온더마켓 쪽 완화 조치는 restaurant.signal.ts 같은 목록 조회에서 @Arg.Query("skip", () => Int, { nullable: true }) skip: number | null을 @Arg.Query("skip", () => Int) skip: number로 바꾸는 식이었습니다. 서비스 계층은 이미 값이 있을 때만 필터를 적용하고 있어 시그니처만 손댔습니다.

Outcome & trade-off

타입 서버와 빌드는 정상으로 돌아왔고, 3주 동안 인자 contract가 빡빡해지는 대가를 치렀습니다.

Outcome 2ⁿ → n, 프레임워크 레벨에서 해결

nullable 인자 수와 무관하게 파생 타입이 선형으로 계산됩니다. 프레임워크 수정 이후에는 signal에 nullable을 다시 자유롭게 쓰고 있고, 현재 100개가 넘는 nullable 인자에서도 같은 증상은 재발하지 않았습니다.

Trade-off 완화 기간 동안 클라이언트가 값을 항상 넘겨야 함

nullable을 뺀 3주 동안은 목록 조회마다 statuses·skip·limit을 클라이언트가 채워 보내야 했고, "생략하면 전체"라는 API 유연성을 포기했습니다. 프레임워크 반영 후 필요한 곳부터 되돌렸습니다.

프레임워크 코드를 직접 고치지 않고 두 단계로 나눈 이유는, 패키지를 포크해 패치하면 이후 버전을 따라갈 때마다 같은 패치를 얹어야 하기 때문이었습니다. 당장 출시를 막는 증상은 코드에서 걷어내고, 근본 원인은 원래 주인이 고치도록 넘기는 편이 1인 개발에서 유지 비용이 가장 낮았습니다.
