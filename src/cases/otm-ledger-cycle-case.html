OnTheMarket · Solved issue 04

장부·상품 서비스의 순환 의존 해소

견적 요청 기능을 붙이면서 장부·상품·식당 서비스가 서로를 주입하는 DI 순환이 생겼습니다. 두 서비스에 걸치는 작업을 resolver의 두 호출로 나눠 의존 방향을 장부 → 유통사·식당 한쪽으로 정리했습니다.

Problem & constraints

장부 서비스가 유통사·식당 서비스를 새로 필요로 하게 됐습니다.

온더마켓은 음식점 점주가 식자재 유통사를 비교해 주문하는 B2B 서비스입니다. 점주는 매번 비슷한 식자재를 반복해서 사기 때문에, 자주 사는 품목을 장부(Ledger)에 저장해 두고 그 목록을 기준으로 유통사 가격 비교·주문·견적 요청을 시작하는 구조로 만들었습니다. 이 사례에 얽힌 모델은 아래 여섯 개입니다.

Restaurant 음식점
점주의 매장. 사업자·주소·배송 시간대·수령 방식·전화번호를 갖고, 보유 장부 id 배열 ledgers[]와 즐겨찾는 유통사 favoriteDistributors[]를 들고 있습니다. 알림톡의 수신 번호와 식당명이 여기서 나옵니다.
Distributor 유통사
식자재 공급사. 사업자·정산 계좌·토스 셀러 정보와 함께 상품별 가격표 pricingCatalogs[](catalog·costPrice·sellingPrice·date)를 갖습니다. 최저가 계산 listInPriceRank는 이 가격표를 장부 품목에 대입해 총액 순으로 정렬합니다.
Catalog 상품 마스터
이름·단위·규격·masterCode·status(active/master/inactive)를 가진 상품 원장. 장부 품목, 주문 품목, 유통사 가격표가 모두 이 id를 참조하므로, 상품을 비활성화하면 참조를 함께 정리해야 합니다.
Ledger 장부
restaurantId·name·lineItems[](catalog·quantity·unitPrice)·status(active/quote/closed/shared). 품목 추가·제거·수정 API와 장바구니 URI 변환이 붙어 있어, 점주가 반복 주문할 품목 리스트이자 유통사 비교의 출발점으로 쓰였습니다.
BidTicket 입찰권
distributorId와 restaurant의 쌍. 유통사가 "이 식당에 공급하겠다"고 등록한 기록이고, 견적 요청에서는 한 식당에 몇 곳의 유통사가 입찰했는지 세는 단위입니다.
Order 주문
장부에서 고른 lineItems[]가 특정 distributor·배송일·총액과 함께 확정된 기록. 결제 승인은 PG(토스페이먼츠)가 처리하고, 서버는 결과 상태만 받아 적습니다.

2025년 11월에 붙인 견적 요청 기능은, 점주가 장부를 status: "quote"로 올리면 유통사들이 BidTicket으로 입찰하고, 매일 저녁 배치(@Schedule.Cron)가 입찰 수가 threshold(3) 이상인 음식점에 최저가 유통사와 가격을 카카오 알림톡으로 보내는 흐름입니다. 최저가는 DistributorService.listInPriceRank, 전화번호와 식당명은 RestaurantService가 갖고 있었으므로, 배치를 담는 LedgerService가 이 두 서비스를 주입받아야 했습니다.

Observed before

상품·식당 서비스가 이미 장부 서비스를 보고 있어 순환이 생겼습니다.

기존 관계는 세 갈래였습니다. RestaurantService는 식당 생성 시 기본 장부를 만들고 그 id를 restaurant.ledgers에 넣으려고(initLedger) LedgerService를 주입받았고, CatalogService는 상품 비활성화 시 모든 장부의 lineItems에서 그 상품을 지우려고(removeAllLineItemsByCatalogId) 역시 LedgerService를 주입받았습니다. DistributorService는 가격표 갱신과 입찰 처리를 위해 원래부터 CatalogService·RestaurantService·BidTicketService에 의존했습니다. 모델 레벨에서는 Restaurant가 장부 id를 들고 있어 방향이 Restaurant → Ledger 한쪽이었지만, 서비스 레벨에서는 LedgerService에 새 의존을 더하는 순간 DI 그래프가 두 곳에서 돌기 시작했습니다.

DistributorService→ CatalogService→ LedgerService→ DistributorService↺ 순환
RestaurantService→ LedgerService→ RestaurantService↺ 순환

Solution

상품·식당 서비스에서 장부 의존을 빼고, 걸치는 작업은 Signal에서 두 번 호출했습니다.

장부는 식당·유통사·상품을 알아야 하지만 그 반대는 아니어도 된다고 보고, 의존 방향을 장부 → 유통사·식당 한쪽으로만 두기로 했습니다. CatalogService.inactivateCatalog는 상품 상태만 바꾸고, 장부에서 품목을 지우는 호출은 GraphQL resolver인 catalog.signal.ts가 이어서 하도록 옮겼습니다. initLedger는 RestaurantService에서 LedgerService로 옮겨 장부를 만든 뒤 restaurantService로 식당의 ledgers를 갱신하게 했고, restaurant.signal.ts가 ledgerService.initLedger를 부르게 했습니다.

LedgerService→ DistributorService· RestaurantService단방향 · Catalog·Restaurant는 Ledger를 모름
01 · 의존 제거Catalog · Restaurant에서 @Srv() ledgerService 삭제
→
02 · 책임 이동initLedger를 LedgerService로
→
03 · 조합 지점Signal이 두 서비스를 순서대로 호출

Code change

서비스 안에서 이어지던 두 작업을 resolver의 두 줄로 나눴습니다.

Beforecatalog.service.ts가 ledgerService를 직접 호출
@Service("CatalogService")
export class CatalogService extends DbService(db.catalogDb) {
  @Srv() ledgerService: srv.LedgerService;

  async inactivateCatalog(catalogId: string) {
    const catalog = await this.getCatalog(catalogId);
    await catalog.set({ status: "inactive" }).save();
    await this.ledgerService
      .removeAllLineItemsByCatalogId(catalogId);
  }
}
Aftercatalog.signal.ts에서 두 서비스를 차례로 호출
// catalog.signal.ts
@Mutation.Admin(() => Boolean)
async inactivateCatalog(
  @Arg.Body("catalogId", () => String) catalogId: string
) {
  await this.catalogService.inactivateCatalog(catalogId);
  await this.ledgerService
    .removeAllLineItemsByCatalogId(catalogId);
  return true;
}

// ledger.service.ts
@Srv() distributorService: srv.DistributorService;
@Srv() restaurantService: srv.RestaurantService;

한 달 뒤 후속 커밋에서는 createRestaurant 직후에도 ledgerService.initLedger(restaurant.id)를 호출하도록 보완해, 첫 장부 목록 조회 전에도 기본 장부가 생기도록 했습니다.

Outcome & trade-off

순환은 사라졌지만, 두 호출 사이의 원자성은 포기했습니다.

Outcome Ledger → Distributor · Restaurant 단방향

견적 요청·입찰 알림 배치를 LedgerService 안에 두고도 DI 순환 없이 서버가 뜨게 됐습니다. Catalog·Restaurant 서비스는 장부의 존재를 모릅니다.

Trade-off 상품 비활성 후 장부 정리 실패 가능

첫 호출은 성공하고 두 번째가 실패하면 상품은 비활성인데 장부에는 품목이 남는 중간 상태가 생깁니다. 트랜잭션이나 보상 로직은 두지 않았습니다.

원자성을 일단 포기해도 된다고 판단한 근거는 이 흐름에 현금이 오가지 않는다는 점이었습니다. 결제 승인과 취소는 PG가 처리하고, 여기서 끊기는 것은 상품 상태와 장부 품목 정리뿐이라 중간 상태가 남아도 돈이 잘못 움직이지는 않습니다. 덧붙여 상품 비활성화는 관리자가 드물게 수행하는 작업이라 다음 정리 호출로 회복할 수 있었고, 1인 개발에서는 기능을 먼저 내보내는 속도가 우선이었습니다. 호출 빈도가 늘어나면 두 호출을 하나의 트랜잭션으로 묶거나 실패 시 재실행할 수 있는 정리 배치를 두려는 계획이었습니다.
