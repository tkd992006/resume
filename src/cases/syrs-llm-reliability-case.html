SYRS AI Lab · Solved issue 01

LLM 응답 포맷 안정화

비용 때문에 쓴 gpt-4o-mini의 불안정한 JSON 응답을 런타임 타입 가드와 재시도로 잡고, 그만큼 길어진 대기시간은 스캔 애니메이션으로 흡수했습니다.

Problem & constraints

단가를 맞추려면 gpt-4o-mini를 써야 했는데, 이 모델은 포맷을 자주 어겼습니다.

피부 진단 보고서는 현미경 이미지와 긴 프롬프트를 함께 보내는 호출이라, 한 건당 비용을 감안하면 gpt-4o-mini가 현실적인 선택이었습니다. 문제는 당시 이 모델의 응답 포맷팅이 불안정했다는 점입니다. "JSON으로 답하라"고 지시해도 결과를 그대로 파싱할 수 없는 경우가 이어졌고, HTTP 성공만으로는 진단이 성공했는지 판단할 수 없었습니다. 매장 iPad에서 고객과 상담사가 함께 보는 화면이라 실패를 그대로 노출할 수도 없었습니다.

Observed before

스트림은 정상 종료됐는데 제품이 쓸 수 없는 응답이 반복됐습니다.

실제로 관찰된 실패는 세 가지였습니다. JSON 앞뒤에 "다음은 분석 결과입니다" 같은 설명 문장이 붙어 JSON.parse가 바로 실패하는 경우, 파싱은 되지만 skinAge나 oilWaterBalanceDesc 같은 필수 분석 필드가 빠진 경우, 그리고 고객이 고른 언어와 다른 언어로 응답하는 경우였습니다. 세 경우 모두 서버에서는 정상 응답으로 보였기 때문에, 이 상태로는 결과를 저장하거나 화면에 그릴 수 없었습니다.

Solution

프롬프트의 기대를 런타임 성공 조건으로 옮기고, 실패하면 다시 호출했습니다.

스트림으로 모은 출력에서 첫 {와 마지막 } 사이만 잘라 파싱하고, 최초 진단은 isSkinData, 개선 진단은 isSkinImprovementData 타입 가드로 필수 필드와 값 타입을 검사했습니다. 가드를 통과하지 못하면 정상 결과로 저장하지 않고 오류로 던져 최대 5회까지 다시 시도했고, 개선 진단 프롬프트에는 선택 언어를 다시 명시해 언어 불일치를 줄였습니다.

Outcome & trade-off

포맷은 런타임에서 보장됐고, 길어진 대기는 애니메이션으로 흡수했습니다.

검증을 통과한 응답만 저장되므로 화면이 깨진 결과를 받는 일은 사라졌습니다. 대신 재시도 때문에 최악의 경우 대기시간과 호출 비용이 시도 횟수만큼 늘어나는 트레이드오프가 생겼습니다. 이 시간을 더 줄이는 대신 제품 경험 안에 넣기로 했습니다. 최초 진단용 Loading과 개선 진단용 SolutionLoading에 react-spring 스캔 애니메이션을 두어 기다리는 동안 분석이 진행 중이라는 느낌을 주고, 영·한·일·태 4개 언어 안내와 닫기·처음으로 돌아가기 오류 복구 동선을 연결했습니다. 개선 진단은 최초 진단의 OpenAI 스레드를 이어받아 이전 결과를 비교 맥락으로 사용합니다.

Trade-off

5회는 항상 호출하는 횟수가 아니라 실패했을 때 쓸 수 있는 상한입니다. 그래도 최악의 경우 대기와 비용은 커지므로, 그 시간을 사용자가 견딜 수 있게 만드는 로딩 화면까지가 이 작업의 범위였습니다.

런타임 타입 가드: 필수 필드와 타입, 피부 타입 enum 검증 코드 보기 
function isSkinData(data): data is SkinData {
  if (
    typeof data === "object" &&
    data !== null &&
    "overview" in data &&
    "skinAge" in data &&
    "skinAgingDesc" in data &&
    "sensitivityDesc" in data &&
    "oilWaterBalanceDesc" in data &&
    "type" in data
  ) {
    return (
      typeof data.overview === "string" &&
      typeof data.skinAge === "number" &&
      typeof data.skinAgingDesc === "string" &&
      typeof data.sensitivityDesc === "string" &&
      typeof data.oilWaterBalanceDesc === "string" &&
      (data.type === "typeA" || data.type === "typeB" ||
        data.type === "typeC" || data.type === "typeD" ||
        data.type === "typeE")
    );
  }
  return false;
}

개선 진단용 isSkinImprovementData는 여기에 노화·민감도·유수분 개선 설명 3개 필드를 추가로 요구하는 별도 가드입니다. HTTP 성공이 아니라 이 가드를 통과해야 진단 성공으로 저장됩니다.

스트림 수집과 JSON 추출: threadId를 남기는 실패 경로 코드 보기 
const run = openai.beta.threads.runs
  .stream(thread.id, { assistant_id: prompt.assistantId })
  .on("textDelta", (textDelta) => {
    if (!textDelta.value) return;
    outputParts.push(textDelta.value);
  })
  .on("error", (e) => {
    reject(errors.apiError(e.message, thread.id));
  })
  .on("end", () => {
    const outputText = outputParts.join("");
    // 설명 문장이 붙은 응답에서 JSON 구간만 추출
    const jsonStart = outputText.indexOf("{");
    const jsonEnd = outputText.lastIndexOf("}") + 1;
    /* … 파싱 실패 시 errors.unknownError(…, thread.id) reject … */
    const jsonObject: unknown = JSON.parse(outputText.slice(jsonStart, jsonEnd));

    if (!isSkinData(jsonObject)) {
      reject(errors.jsonParseError("JSON parsing failed. …", thread.id));
    } else {
      jsonObject.threadId = thread.id;
      resolve({ skinData: jsonObject, rawResponse: outputText, threadId: thread.id });
    }
  });

오류를 apiError · jsonParseError · unknownError로 분류하고 모든 오류 메시지에 threadId를 실어 사후 추적이 가능하게 했습니다.
