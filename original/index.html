영수증 한 장으로 “온더마켓이었으면 얼마”를 보여주는 캠페인

앱 설치 전 점주가 영수증 사진만 올리면, 그 날짜의 온더마켓 최저가와 비교해 품목별 차액과 절감액을 보여주는 신규 유입 캠페인입니다. Gemini 구조화 OCR, 카탈로그 매칭 검증, 날짜별 최저가 조회 순서로 처리합니다.

Problem & constraints

가입 전 점주에게 “우리 가게 야채값이 비싼가?”를 영수증 한 장으로 답해야 했습니다.

온더마켓은 음식점 점주가 식자재 유통사를 비교해 주문하는 B2B 서비스인데, 점주 입장에서는 앱을 깔고 장부를 만들기 전까지 “여기서 사면 얼마나 싸지는지”를 알 방법이 없었습니다. 그래서 신규 유입용으로 가입 없이 쓰는 랜딩 페이지를 만들었습니다. 점주가 지금 거래하는 유통사의 영수증이나 납품서 사진을 올리면, 그 영수증 날짜에 같은 품목을 온더마켓 최저가로 샀을 때의 금액을 품목별로 비교해 “이만큼 손해보셨어요”와 연간 환산 절감액을 보여주고, 상세 리포트를 문자로 받겠다며 전화번호를 남기면 영업 리드로 이어지는 흐름입니다. 이 사례에 얽힌 데이터는 아래 세 가지입니다.

Catalog 상품 마스터
온더마켓이 파는 모든 식자재의 원장. 이름·규격·description을 갖고 있고, 유통사 가격표와 주문 품목이 모두 이 id를 참조합니다. 영수증의 품목명을 결국 이 id로 바꿔야 가격을 찾을 수 있습니다.
PricingLog 일일 최저가 기록
매일 17시 배치가 활성 유통사들의 가격표에서 상품별 최저 판매가를 모아 daily_lowest_price 타입으로 저장한 스냅샷. “그 날짜의 온더마켓 최저가”는 이 기록에서 나옵니다.
PriceCompare 진단 요청
점주가 올린 영수증 이미지 한 건. 생성 직후 서버가 OCR과 가격 조회를 돌려 품목별 receiptResult(영수증 단가·온더마켓 단가·차액·매칭 여부)와 기준 날짜를 채우고, 나중에 남긴 전화번호를 같이 담습니다.

어려운 부분은 영수증에 적힌 “양파 10kg”, “감자(상)” 같은 축약 품목명을 카탈로그 id로 신뢰할 수 있게 연결하는 일과, 영수증 날짜에 해당하는 최저가 기록이 없을 때도 결과 화면이 비지 않게 하는 일이었습니다. 점주가 처음 보는 화면에서 엉뚱한 상품과 비교되거나 빈 결과가 나오면 캠페인 자체가 신뢰를 잃기 때문입니다.

장부·상품 서비스의 순환 의존 해소

가입 후 주문을 시작하지 않거나 가격 확인 단계에 도달하지 못한 점주도 서비스의 가격을 경험할 수 있도록, 튜토리얼에서 식자재를 고르고 견적을 요청한 뒤 카카오톡으로 결과를 받는 흐름을 만들었습니다. 이 알림에 필요한 음식점 정보와 유통업체 가격을 조회하면서 서비스 간 의존이 순환하지 않도록 구조를 정리했습니다.

Problem & constraints

주문을 시작하기 전에도 “여기서 사면 얼마인지” 알 수 있어야 했습니다.

온더마켓은 음식점 점주가 식자재를 고르고 유통업체를 비교해 주문하는 서비스입니다. 기존에는 주문할 식자재를 담은 뒤 유통업체를 선택하는 단계까지 가야 업체별 가격을 확인할 수 있었습니다. 가입과 온보딩을 마쳐도 주문을 시작하지 않거나 그 단계까지 도달하지 못하면, 점주는 실제 구매 가격을 확인하지 못한 채 이탈할 수 있었습니다.

그래서 주문 흐름을 끝까지 진행하지 않아도 가격을 경험할 수 있는 튜토리얼을 만들었습니다. 점주가 자주 사는 식자재를 고르면 예상 최저가를 보여주고, “견적받고 온더마켓 시작하기”로 견적을 요청할 수 있게 했습니다. 이후 공급 가능한 유통업체의 가격을 비교해 카카오톡으로 알려주고, 알림에서 업체 비교·주문 화면으로 다시 이어지도록 했습니다.

  1. 튜토리얼에서 구매할 식자재와 수량을 선택하고 예상 가격을 확인합니다.
  2. 견적을 신청하면 선택한 품목을 저장하고, 결과가 준비되면 카카오톡으로 안내합니다.
  3. 점주는 알림에 담긴 최저가 업체·금액을 보고 업체 비교 또는 주문 화면으로 이동합니다.

주문 과정에서 추천 유통업체가 아직 없는 점주도 같은 견적 요청을 할 수 있습니다. 알림의 대상은 실제로 견적을 신청한 음식점입니다. 가입만 했거나 주문 이력이 없다는 이유로 자동 발송하는 조건은 아닙니다.

OnTheMarket · Solved issue 05

타입 서버를 느리게 만든 nullable 인자 타입 폭발 추적

웹 빌드가 10분을 넘기기 시작했을 때, 타입이 퍼져 나가는 곳은 signal뿐이라고 보고 프레임워크의 인자 튜플 타입에서 2ⁿ으로 불어나는 지점을 찾아냈습니다.

Problem & constraints

코드는 조금씩 늘었을 뿐인데 타입 검사 시간이 감당이 안 되기 시작했습니다.

온더마켓은 AkanJS 프레임워크 위에서 만든 서비스입니다. AkanJS에서는 GraphQL resolver를 *.signal.ts에 선언하면, 그 메서드 시그니처 하나에서 클라이언트 fetch 함수, store의 queryArgsOf…, 페이지 init 타입까지 TypeScript 타입으로 자동 파생됩니다. 서버 코드를 한 번만 쓰면 클라이언트 타입이 따라오는 구조라, 목록 조회에는 statuses·skip·limit·sort처럼 생략 가능한 필터 인자를 { nullable: true }로 자유롭게 붙여 왔습니다.

2025년 8월 중순, 유통사·상품·장부·식당 목록 화면을 한꺼번에 붙이면서 전체 API 인자 중 nullable 인자가 132개까지 늘었습니다. 그 무렵부터 에디터 타입 서버가 응답을 멈추기 일쑤였고, 웹 빌드는 10분을 넘겼습니다. 1인 개발이라 빌드 한 번이 곧 배포 주기여서, 출시 전 검수 일정 안에 원인을 찾아야 했습니다.

Observed before

타입이 퍼지는 곳은 signal뿐이니, 프레임워크의 인자 타입부터 열어 봤습니다.

서비스나 문서 모델은 타입이 그 파일 안에서 끝나지만, signal 메서드의 인자 타입은 프레임워크가 튜플로 받아 앱의 모든 클라이언트 타입으로 다시 찍어 냅니다. 그래서 느려진 원인이 어디든 증폭되는 지점은 signal이라고 보고, @akanjs/signal의 gql.ts에서 인자 튜플을 가공하는 FilterOutInternalArgs를 읽었습니다. 이 타입은 튜플을 앞에서부터 재귀하면서 Head extends undefined | null로 nullable 인자를 판정하고, nullable이면 [...Acc, Head?]로 optional 요소를 하나씩 쌓는 방식이었습니다.

문제는 infer Head로 뽑은 타입 파라미터에 조건부 타입을 걸면 TypeScript가 유니온을 분배한다는 점이었습니다. string | null은 string 가지와 null 가지로 갈라지고, 누적 중이던 튜플도 둘로 복제됩니다. nullable 인자를 하나 지날 때마다 튜플 유니온이 두 배가 되니, 인자 7개짜리 목록 조회 하나가 128개의 튜플 조합을 만들고, 그 조합이 fetch 함수·store·init 타입마다 다시 계산됐습니다.

nullable 인자 n개→ 분배 조건부 타입→ 튜플 유니온 2ⁿ개→ 파생 타입마다 재계산

Solution

당장은 nullable을 걷어내 출시를 지키고, 근본 수정은 프레임워크에 반영되게 했습니다.

먼저 온더마켓 쪽에서 목록 조회의 statuses·skip·limit과 검색 필터 인자에서 nullable을 빼고 클라이언트가 항상 값을 넘기도록 바꿨습니다. 마지막 인자인 sort만 nullable로 남겼는데, 튜플 끝에 하나 있는 nullable은 분기가 한 번뿐이라 부담이 없었기 때문입니다. 8월 19일부터 25일까지 두 커밋에 걸쳐 132개였던 nullable 인자를 80개, 다시 52개로 줄였고, 타입 서버와 빌드가 다시 돌아왔습니다.

동시에 원인 위치와 재현 조건을 AkanJS 쪽에 공유했고, 8월 28일 프레임워크 PR에서 FilterOutInternalArgs가 세 단계로 다시 쓰였습니다. 내부 인자 제거(FilterInternalArgs)와 타입 변환(ConvertArgs)을 분리하고, nullable 판정은 분배가 일어나지 않는 null extends Head로 바꾼 뒤, 첫 nullable 인자를 만나는 순간 나머지를 Partial<T> 한 번으로 처리합니다. 분기가 사라져 인자 수에 선형으로 끝납니다. 온더마켓은 9월 초 이 수정이 담긴 0.9.44로 올렸습니다.

LLM 응답 포맷 안정화

비용 때문에 쓴 gpt-4o-mini의 불안정한 JSON 응답을 런타임 타입 가드와 재시도로 잡고, 그만큼 길어진 대기시간은 스캔 애니메이션으로 흡수했습니다.

Problem & constraints

단가를 맞추려면 gpt-4o-mini를 써야 했는데, 이 모델은 포맷을 자주 어겼습니다.

피부 진단 보고서는 현미경 이미지와 긴 프롬프트를 함께 보내는 호출이라, 한 건당 비용을 감안하면 gpt-4o-mini가 현실적인 선택이었습니다. 문제는 당시 이 모델의 응답 포맷팅이 불안정했다는 점입니다. "JSON으로 답하라"고 지시해도 결과를 그대로 파싱할 수 없는 경우가 이어졌고, HTTP 성공만으로는 진단이 성공했는지 판단할 수 없었습니다. 매장 iPad에서 고객과 상담사가 함께 보는 화면이라 실패를 그대로 노출할 수도 없었습니다.

Observed before

스트림은 정상 종료됐는데 제품이 쓸 수 없는 응답이 반복됐습니다.

실제로 관찰된 실패는 세 가지였습니다. JSON 앞뒤에 "다음은 분석 결과입니다" 같은 설명 문장이 붙어 JSON.parse가 바로 실패하는 경우, 파싱은 되지만 skinAge나 oilWaterBalanceDesc 같은 필수 분석 필드가 빠진 경우, 그리고 고객이 고른 언어와 다른 언어로 응답하는 경우였습니다. 세 경우 모두 서버에서는 정상 응답으로 보였기 때문에, 이 상태로는 결과를 저장하거나 화면에 그릴 수 없었습니다.

Solution

프롬프트의 기대를 런타임 성공 조건으로 옮기고, 실패하면 다시 호출했습니다.

스트림으로 모은 출력에서 첫 {와 마지막 } 사이만 잘라 파싱하고, 최초 진단은 isSkinData, 개선 진단은 isSkinImprovementData 타입 가드로 필수 필드와 값 타입을 검사했습니다. 가드를 통과하지 못하면 정상 결과로 저장하지 않고 오류로 던져 최대 5회까지 다시 시도했고, 개선 진단 프롬프트에는 선택 언어를 다시 명시해 언어 불일치를 줄였습니다.

function isSkinData(data): data is SkinData {
  if (
    typeof data === "object" &&
    data !== null &&
    "overview" in data &&
    "skinAge" in data &&
    "skinAgingDesc" in data &&
    "sensitivityDesc" in data &&
    "oilWaterBalanceDesc" in data &&
    "type" in data
  ) {
    return (
      typeof data.overview === "string" &&
      typeof data.skinAge === "number" &&
      typeof data.skinAgingDesc === "string" &&
      typeof data.sensitivityDesc === "string" &&
      typeof data.oilWaterBalanceDesc === "string" &&
      (data.type === "typeA" || data.type === "typeB" ||
        data.type === "typeC" || data.type === "typeD" ||
        data.type === "typeE")
    );
  }
  return false;
}
