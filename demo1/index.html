OnTheMarket · Solved issue 01

주문 목록 관계 데이터 경량화

10초 가까이 걸리던 점주 주문 목록의 관계 데이터 의존을 정리하고, 목록·중첩 관계에 Light 모델 경계를 세워 눈에 띄게 빠르게 만들었습니다.

Problem & constraints

음식점 주문 목록 화면이 뜨는 데 10초 정도씩 걸렸습니다.

점주가 앱에서 주문 내역 탭을 열면 목록이 뜨기까지 10초 가까이 기다려야 했습니다. 주문 카드는 판매자명·연락처·납품서용 사업자 정보를 바로 보여줘야 했으므로, 주문(Order)이 유통사·식당 데이터를 필드로 들고 있는 구조 자체는 유지해야 했습니다.

Framework rule · Full & Light

akanjs는 모델마다 Full·Light 두 벌의 GraphQL fragment를 기본으로 만들고, 배열 조회에는 Light를 자동으로 씁니다.

akanjs에서 모델 하나를 정의하면 fragment가 두 벌 생깁니다. Light는 via(Object, [필드 목록])으로 고른 목록용 필드만 담고, Full은 Light를 포함한 전체 필드를 담습니다. 조회 결과가 배열이면 프레임워크가 Light fragment를, 단건이면 Full fragment를 알아서 고릅니다. 그래서 관계 필드까지 Light 타입으로 선언해 이 규칙을 존중하면, 목록 응답을 얇게 유지하는 일은 프레임워크가 대신 해 줍니다.

자동 규칙의 한계

배열 조회는 getLightModelRef로 Light fragment를 고르지만, fragment 본문은 관계 필드에 선언된 타입을 그대로 따라 재귀로 펼쳐집니다. Light 모델 안의 관계 필드가 Distributor처럼 Full 타입이면 목록 안에서 Full fragment가 다시 열립니다.

Observed before

관계 필드가 자동으로 전부 조회되면서 가격표와 이미지 메타데이터까지 따라왔습니다.

주문 목록 조회 자체는 배열이라 LightOrder fragment로 나갔지만, 1인 개발 편의상 그 안의 distributor·restaurant 관계 필드는 Full 타입으로 선언해 둔 채였습니다. fragment가 선언된 타입을 따라 펼쳐지면서 목록 20건마다 유통사 Full fragment가 붙고, 그 안의 상품별 가격표 약 100개가 Catalog와 image 메타데이터까지 연쇄로 따라와 서버가 받아 오는 데이터가 너무 많아졌습니다.

Solution

데이터 의존 관계를 그려 보고, 목록에 필요한 필드와 아닌 필드를 나눴습니다.

Order → Distributor → PricingCatalog → Catalog → image로 이어지는 관계 그래프를 따라가며 목록이 실제로 읽는 값을 확인했습니다. 판매자명·연락처·사업자번호·표시 주소처럼 카드와 납품서에 쓰는 값은 남기고, 상품별 가격표·정산 계좌·PG 입점 상태처럼 가격 관리나 설정 화면에서만 쓰는 값은 뺐습니다.

경계

OnTheMarket · Solved issue 02

PG 페이지를 다녀온 뒤 WebView 레이아웃 복원

다른 앱으로 내보내지 않고 웹뷰 안에서 결제사 페이지를 오가게 하면서 생긴 inset 문제를 한 단계씩 좁혀, 복귀 시 safe-area·viewport가 다시 계산되도록 native에서 맞춰줬습니다.

Problem & constraints

결제는 직접 제어할 수 없는 외부 페이지를 웹뷰 안에서 다녀와야 했습니다.

앱 안에서 결제를 하려면 직접 제어하기 곤란한 TossPayments 같은 외부 결제사(PG) 페이지를 거쳐야 했습니다. 팝업이나 별도 앱·브라우저로 나갔다가 다시 돌아오는 방식은, 휴대폰에 시간을 많이 쓰고 싶어 하지 않고 연령대가 꽤 있는 식당 점주들에게 어려울 수 있다고 판단했습니다. 그래서 다른 앱으로 나가는 리다이렉트를 최소화하고, 웹뷰 안에서 실제 URL을 바꿔 결제사 페이지로 갔다가 돌아오는 플로우를 택했습니다.

기존 웹앱 구조는 웹페이지와 앱을 같은 코드로 운영하기 위해 휴대폰 화면 전체를 웹뷰로 덮고, 노치·홈 인디케이터 같은 safe-area(inset)는 Capacitor로 감지해 CSS 값으로 웹 레이아웃에 넘겨주는 방식이었습니다. 내부 화면에서는 웹이 safe-area를 소유했습니다.

외부 PG 페이지에서는 이 방법을 쓸 수 없었습니다. PG사 웹사이트는 CSS로 제어할 수 없는 외부 문서라 native 단에서 WebView의 inset을 직접 다뤄야 했고, 그 과정에서 아래 문제들이 순서대로 나타났습니다.

내부 주문 화면웹이 safe-area 소유→ 외부 PG 페이지native가 inset 소유→ 카드·은행 앱intent / scheme으로 OS에 위임→ 내부 결과 화면다시 웹이 소유해야 함

Observed before

inset을 안 넣으면 결제 버튼이 가려지고, 넣으면 돌아온 화면이 깨졌습니다.

처음에는 PG 페이지를 그냥 두었습니다. 웹뷰가 화면 전체를 덮는 구조라 외부 문서는 inset이나 margin 없이 떴고, Android에서 메뉴·홈·뒤로가기 3버튼 내비게이션 바를 켜 둔 기기에서는 시스템 바가 결제사의 “결제하기” 버튼을 그대로 덮었습니다. 불편한 수준이 아니라 결제 자체가 불가능한 경우였습니다.

그래서 외부 URL일 때 native에서 URL을 감지해 inset을 넣어줬더니, 결제를 마치고 앱 페이지로 돌아오면 바텀 탭이 위로 떠 버렸습니다. 복귀 시점에 inset과 safeArea를 초기화하는 코드를 넣었더니, 이번에는 바텀 탭이 화면 아래에 박혀 버렸습니다.

서비스나 문서 모델은 타입이 그 파일 안에서 끝나지만, signal 메서드의 인자 타입은 프레임워크가 튜플로 받아 앱의 모든 클라이언트 타입으로 다시 찍어 냅니다. 그래서 느려진 원인이 어디든 증폭되는 지점은 signal이라고 보고, @akanjs/signal의 gql.ts에서 인자 튜플을 가공하는 FilterOutInternalArgs를 읽었습니다. 이 타입은 튜플을 앞에서부터 재귀하면서 Head extends undefined | null로 nullable 인자를 판정하고, nullable이면 [...Acc, Head?]로 optional 요소를 하나씩 쌓는 방식이었습니다.

문제는 infer Head로 뽑은 타입 파라미터에 조건부 타입을 걸면 TypeScript가 유니온을 분배한다는 점이었습니다. string | null은 string 가지와 null 가지로 갈라지고, 누적 중이던 튜플도 둘로 복제됩니다. nullable 인자를 하나 지날 때마다 튜플 유니온이 두 배가 되니, 인자 7개짜리 목록 조회 하나가 128개의 튜플 조합을 만들고, 그 조합이 fetch 함수·store·init 타입마다 다시 계산됐습니다.

nullable 인자 n개→ 분배 조건부 타입→ 튜플 유니온 2ⁿ개→ 파생 타입마다 재계산

Solution

당장은 nullable을 걷어내 출시를 지키고, 근본 수정은 프레임워크에 반영되게 했습니다.

먼저 온더마켓 쪽에서 목록 조회의 statuses·skip·limit과 검색 필터 인자에서 nullable을 빼고 클라이언트가 항상 값을 넘기도록 바꿨습니다. 마지막 인자인 sort만 nullable로 남겼는데, 튜플 끝에 하나 있는 nullable은 분기가 한 번뿐이라 부담이 없었기 때문입니다. 8월 19일부터 25일까지 두 커밋에 걸쳐 132개였던 nullable 인자를 80개, 다시 52개로 줄였고, 타입 서버와 빌드가 다시 돌아왔습니다.

동시에 원인 위치와 재현 조건을 AkanJS 쪽에 공유했고, 8월 28일 프레임워크 PR에서 FilterOutInternalArgs가 세 단계로 다시 쓰였습니다. 내부 인자 제거(FilterInternalArgs)와 타입 변환(ConvertArgs)을 분리하고, nullable 판정은 분배가 일어나지 않는 null extends Head로 바꾼 뒤, 첫 nullable 인자를 만나는 순간 나머지를 Partial<T> 한 번으로 처리합니다. 분기가 사라져 인자 수에 선형으로 끝납니다. 온더마켓은 9월 초 이 수정이 담긴 0.9.44로 올렸습니다.

Code change

분배되는 조건부 타입 하나를 비분배 판정과 Partial 한 번으로 바꿨습니다.

Before@akanjs/signal gql.ts · nullable마다 튜플이 두 갈래로
export type FilterOutInternalArgs<
  T extends any[], Acc extends any[] = []
> = T extends readonly [infer Head, ...infer Rest]
  ? IsInternalArg<Head> extends true
    ? FilterOutInternalArgs<Rest, Acc>
    // Head가 string | null이면 여기서 분배 →
    // Acc가 [.., string]과 [.., null?] 둘로 복제
    : Head extends undefined | null
      ? FilterOutInternalArgs<Rest, [...Acc, ConvertArg<Head>?]>
      : FilterOutInternalArgs<Rest, [...Acc, ConvertArg<Head>]>
  : Acc;
After비분배 판정 + 첫 nullable부터 Partial 한 번
type FilterInternalArgs<T extends any[]> =
  T extends [...infer Rest, infer Last]
    ? IsInternalArg<Last> extends true
      ? FilterInternalArgs<Rest> : T
    : [];

type PartialNullableArgs<T extends any[]> =
  T extends [infer Head, ...infer Rest]
    ? null extends Head        // 분배 없음
      ? Partial<T>             // 나머지를 한 번에
      : [Head, ...PartialNullableArgs<Rest>]
    : [];

export type FilterOutInternalArgs<Args extends any[]> =
  PartialNullableArgs<ConvertArgs<FilterInternalArgs<Args>>>;
